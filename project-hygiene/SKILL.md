# 预防项目无效增生

在完成任务的过程中保持项目容易理解和维护。每次工作都考虑新增会带来什么长期负担，而不只是这次能否交付。默认先理解并维护现有内容；确有独立用途时再新增，不把“少文件”变成限制必要实现的硬指标。

## 动手前先找归属

读适用的项目约定与本次相关文件，弄清已有目录、入口和文档分别负责什么。围绕用户要求的效果确定改动范围，不因为任务提到了写作、测试或验证，就自动安排一份新文档、一套脚本或一个新文件夹。

新增前先判断：已有位置是否能承担？是否增加了独立且持续需要的用途？以后内容变化时，是否会多出一份必须同步的副本？这些是自行作出选择的依据，不要求把每个文件都交给用户审批。

## 写作与结构选择

- 优先更新负责这项内容的现有文件；需要补充时写入对应部分。只有受众、用途、规模或维护方式确实需要独立时才拆分，沿用项目已有组织方式。
- 围绕读者实际需要写内容，不因模板有一栏就填一栏，不因“完整一些”“以后可能用到”增加指南、摘要、索引、占位或配套制度。用户明确需要的交付物正常提供。
- 同一事实或决定尽量在负责定义它的位置维护；其他地方有阅读需要才引用。不要把每次进度更新复制到所有入口，也不要为消除重复又加多层跳转。
- 替换内容时一并处理本次涉及的旧说明和引用，避免新旧两套继续演化。“留个入口”“保留兼容”“归档一下”需要实际使用依据，不能成为默认收尾动作。
- 必要的新文件应有明确职责并接入实际使用流程；不为显得结构完整预建空目录，也不把一次任务的步骤逐个映射成永久文件。

## 测试与工作产物

- 先复用现有测试入口，按实际风险验证；需要持续回归的行为可增加有用测试，一次性尝试不自动成为永久脚本。
- 临时调查优先直接运行命令或使用临时位置。日志、截图、解析结果和编译产物沿用项目已有的生成目录，同类检查复用固定位置；需要比较历史结果时再按实际需要留存。
- 验证结论按需更新已有开发记录、验收项或 Issue。普通过程与结果可直接回复用户，不每做一次测试就新增报告、说明书或维护规范。
- 完成后处理自己产生的一次性文件和被替代内容，保留必要的失败证据。不要把共享输出、本机配置、用户数据或他人工作当作可随手清理的缓存。

## 随任务维护与收尾

交付前看一遍实际差异：新增是否确有用途，能否在已有位置完成；本次是否制造了重复资料、失效引用或无人维护的残留。能在授权范围内收尾的就处理好，不把维护责任推给以后。

既有杂物只在与本次任务有关时处理；发现无关问题可简要指出，不自动扩大为全仓审查。删除前核实消费者和恢复方式，尤其保留仍保护数据或行为的兼容定义、回归测试与构建输入；文件旧、名字像临时文件或静态搜索无命中，都不足以证明可删。

沿用项目现有的恢复、验证和发布约定，不另造一套流程。完成请求和必要验证后停止，不以新文档、新目录或更多规则证明工作做过。
