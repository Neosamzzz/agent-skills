# 预防项目无效增生

在完成任务的过程中保持项目容易理解和维护。每次工作都考虑新增会带来什么长期负担，而不只是这次能否交付。默认先理解并维护现有内容；确有独立用途时再新增，不把“少文件”变成限制必要实现的硬指标。

## 先理解层级，再组织内容

必须先理解内容之间的分类与归属：哪些对象同级，哪些是父项，哪些是子项，再安排目录、章节、表格和回复。同级对象并列，子项归入对应父项；严禁把类别、对象、属性和处理意见混在同一层平铺。层级必须表达实际关系，严禁先罗列内容，再靠标题、缩进或排比伪装成有序结构。

清单与表述必须先确定父级分类，再将具体对象及其信息归入对应层级。路线类文档按发展阶段与前置依赖组织，每个阶段承载所属对象及其关系。严禁把不同归属的内容串成一长排并列项，严禁把父项和子项当作同级内容排列。同一对象的信息必须在所属条目内合并维护；补充时先判断它属于哪个已有对象，再修改对应位置。

动手前必须先查看项目目录树、适用约定及相关文件，识别内容类别、共同归属及上下层级。同属一类的项目或模块，必须先归入共同父目录，再各自组织内部内容；严禁把不同层级的内容平铺在根目录。各模块专属的代码、配置、测试和说明必须归入对应模块，根目录只保留项目入口与跨模块共用内容。

发现本次涉及的内容层级混乱、模块内容散落根目录或公共目录时，必须先直接整理，再继续开发：建立或复用共同父目录及对应模块目录，移动散落内容，合并重复文件，同步修正构建路径、脚本和文档引用，并验证原有入口仍可使用。严禁以“沿用现有结构”为由延续散落状态，严禁只增加索引或解释而不整理实际文件。整理限于本次涉及的模块及其引用，不扩展到无关模块。

按项目、模块和功能组织内容：一个归属明确的目录承载对应功能，再按实际需要细分代码、资源、测试与说明。严禁仅按“方案、进度、研究、说明”等产出类型，将同一功能拆散到根目录、公共文档目录和多个模块中；严禁在功能目录之外另建一套需要同步维护的文档体系。跨模块共用的资料才放到共同层级，构建与临时产物沿用项目规定的位置。

新增前先判断已有位置能否承载、是否确有独立且持续的用途、是否会制造重复维护。这些由执行者自行判断，不要求用户逐个指定文件位置，也不为每项功能机械创建一套目录。

## 写作与结构选择

- 文档只保留实际使用需要的内容：环境搭建与启动步骤、当前采用的规则、必要的参数和接口说明。教程写清前置条件与操作步骤，让读者照着就能用。
- 改动内容与必要原因写入 Git 提交信息。文档随规则、用法或必要限制的变化直接更新原文，历史通过 Git 查阅。除明确以日志或变更记录为职责的位置外，严禁在文档中写“取消了”“不做某项”等变更叙述或弃用说明；必须删除被放弃的方案及其解释，直接写当前采用的内容，严禁换词保留同类叙述。排查过程、测试经过和交接叙述同样不得混入普通文档。
- 直接写当前采用什么、怎么操作。严禁将聊天式解释直接追加到文档；补充内容必须融入已有章节或条目，使用简短的书面表述。注释和补充说明仅在影响正确使用或必要判断时保留，简短写一次；禁止使用“不能说明……”“本次仅……”“不代表……”“不是……”“以最新……为准”等解释性文字，也不复述代码或正文已经表达的内容。
- 整理文档前必须检查它引用的文档、引用它的文档及同主题内容，先确定各自职责和内容归属，再整理内部层级。重复内容必须合并到负责定义它的位置，其他文档只保留各自需要的内容。严禁只重排当前文件的标题，却留下跨文档的重复或矛盾说法；严禁另写关系说明代替实际合并。只有内容确有独立、持续的用途时才拆分文件。
- 围绕读者实际需要写内容，不因模板有一栏就填一栏，不因“完整一些”“以后可能用到”增加指南、摘要、索引、占位或配套制度。用户明确需要的交付物正常提供。
- 同一功能的具体说明只在所属位置维护。严禁在根 README、上级目录、功能目录和代码注释中重复铺写功能说明、限制、进度或注意事项。上层索引只保留帮助找到内容的入口；严禁给每段说明附加“详见某处”，或新增“文档关系”等章节串联文件。代码注释只解释局部实现中不直观的原因。
- 正文和回复必须直接说清当前问题；链接仅用于实际需要打开的入口或核查依据。严禁用文件路径、链接清单代替回答，严禁为了证明查过而罗列检索命中、操作过程和重复依据，严禁让读者跨文件拼接本可当场说清的结论。
- 版本说明按版本简述功能变化、修复、必要升级操作和已知问题；严禁写成启动、排查、测试或部署流水。普通功能文档直接写当前功能与用法，不复制版本说明。
- 文档更新必须先做减法，再做加法：先检查本次涉及的已有内容，删除失效、重复和已被替代的表述，合并重叠内容并处理相关引用；再围绕本次开发的功能，在所属位置写清功能本身和当前用法。严禁为了补全文档自行扩写，严禁写成“本次新增了、修改了、验证了什么”的工作记录。严禁先追加新说明，再把旧内容清理留到以后，也严禁留下矛盾说法让读者自行判断。TODO 只保留未完成事项，完成后必须先删除，再按需要在所属文档更新简短的当前用法，严禁转存为完成清单。历史由 Git 保留。
- 必要的新文件应有明确职责并接入实际使用流程；不为显得结构完整预建空目录，也不把一次任务的步骤逐个映射成永久文件。

## 测试与工作产物

- 先复用现有测试入口，按实际风险验证；需要持续回归的行为可增加有用测试，一次性尝试不自动成为永久脚本。
- 临时调查优先直接运行命令或使用临时位置。日志、截图、解析结果和编译产物沿用项目已有的生成目录，同类检查复用固定位置；需要比较历史结果时再按实际需要留存。
- 验证结果在当次回复中简要交代，改动历史由 Git 保留。只有用户明确要求的报告或确有持续使用价值的验证结论才写入文档。
- 完成后必须清理本次产生的一次性文件和已被替代的内容。严禁以“保留失败证据”“以后可能有用”或“便于追溯”为由，留存已解决问题的临时日志、截图、测试文件或另写过程说明。未解决的问题只允许暂存继续定位实际需要的材料，问题解决后必须清理。严禁将共享输出、本机配置、用户数据或他人工作当作本次临时产物清理。

## 随任务维护与收尾

交付前看一遍实际差异：新增是否确有用途，能否在已有位置完成；本次是否制造了重复资料、失效引用或无人维护的残留。能在授权范围内收尾的就处理好，不把维护责任推给以后。

既有杂物只在与本次任务有关时处理；发现无关问题可简要指出，不自动扩大为全仓审查。删除前核实消费者和恢复方式，尤其保留仍保护数据或行为的兼容定义、回归测试与构建输入；文件旧、名字像临时文件或静态搜索无命中，都不足以证明可删。

沿用项目现有的恢复、验证和发布约定，不另造一套流程。完成请求和必要验证后停止，不以新文档、新目录或更多规则证明工作做过。
