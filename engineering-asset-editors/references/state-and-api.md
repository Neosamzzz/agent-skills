# 状态与 API

在实现自动保存、本地 HTTP API、外部 AI 修改或多窗口同步时阅读。这里描述约束，不指定现成框架、端口、文件路径或必须迁移成某一种工程结构。

## 共享的数据语义

Item 使用稳定 ID；工作区实例保留自己的 ID、位置、槽位角色和组合关系。模板定义布局，配方定义具体材料。可复用模板与配方应有清楚的复制／引用策略；一个 Item 对应多条配方时，不要用 Item ID 当成唯一配方 ID。

文件访问路径、图标数据、面板布局、Item 定义与配方分别建模。保存可移植工程时，把需要的图片与图标内嵌或打包，不只保存浏览器 Blob URL 或本机绝对路径。外部文件夹只有经过用户文件选择或已授权的访问渠道才能读取。

将序列化、校验、工程应用封装为共享入口，JSON 导入和 API 更新使用一致的数据约定。后端接受的图像来源、动画元数据、空目录和可选字段，前端必须也能恢复；不能出现写入成功、之后每次同步都加载失败。

## 本地 API 的最小有效结构

可以提供以下能力，按项目已有路由适配：

- 机器可读的 schema：字段、资源键、校验规则与写入方式。
- 小体积摘要：Item ID／名称、配方／模板索引和计数；避免 AI 为找一个 Item 读取整批 Base64 图片。
- 完整工程读写，以及 Item、模板、配方、工作区对象的针对性修改。
- 单次修改的预期 `revision`，成功后的新 revision，失败原因和非阻断 warnings。

默认仅监听回环地址。浏览器写入要求 JSON，并检查来源；静态服务只暴露需要的资源，不把 Git、存储文件或邻接目录发布出来。写入先完整验证，成功后原子落盘；引用错误或缺少输出不能留下半成品修改。

配方的输入／输出取决于槽位角色，游离 Item 不应被隐式当作材料。API 同样校验 Item 引用、唯一身份、有效尺寸、数量和必需输出，不能只在界面拦截。

## 同步时防止覆盖

1. 保存最近一次同步的本地快照和服务端 revision；序列化与提交使用同一份不可变快照。
2. 指针操作、弹窗和未提交输入期间暂缓应用远端修改。`activeElement` 单独不足以代表未提交输入；需要跟踪草稿，处理 blur、change 和节点重新渲染。
3. `await GET` 返回后重新检查本地签名与交互状态，不使用请求发出前的“未修改”判断。
4. 远端变了、本地没变：应用远端。只有本地变了：带已知 revision 提交。
5. 两边都变了：提示采用远端、保留本地或进行项目支持的合并。`409` 后不能仅替换 revision 就静默重试旧内容。
6. PUT 返回后，将实际提交的快照设为基线；不能将返回时的当前页面设为基线，否则等待期间的新编辑会被误判成已保存。

保持对象 ID 稳定。若导入必须重新分配 ID，显式映射组 ID 和引用；同步加载不能每次都生成新 ID，制造伪变化循环。

## 有价值的检查

- 缺少输出和无效引用整批拒绝；存储和 revision 不改变。
- 页面草稿尚未提交时，API 修改不能覆盖输入。
- 服务端写入与页面拖动同时发生，能够延迟、提示冲突并按用户选择完成。
- 修改过程中另一客户端提交旧 revision，返回冲突且不覆盖；取消版本选择有明确行为。
- 导出再导入、服务重启后，图片、动画、分类、配方、尺寸与组合状态能够恢复。
- 取消删除不变，确认只删除当前记录；删除最后一条后，导航与空状态同步更新。
